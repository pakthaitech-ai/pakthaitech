## Important conflicts / effective changes to treat carefully
- **Do not implement a blind template fallback yet.** The desired no-click routine-alert behavior is compatible with the plan only after recipient consent, active partner/phone match, sender verification, approved template, budget/cost policy, rate and duplicate gates, and delivery tracking are all checked in the automatic server-side path. The current Meta `NOT_VERIFIED` result means it must currently stop safely.
- **Free-first is a real constraint.** Sending an approved WhatsApp template outside the 24-hour customer-service window may incur a charge. An approved template is not proof that its send is free. Do not automatically send paid templates without explicit approval of the messaging-cost policy. Do not activate Twilio/Resend as a workaround; neither bypasses Meta verification and both remain outside the selected free-first release.
- **Template sender consent gap:** the current `handleWhatsAppSend` code checks the notification is a partner lead and checks live Meta status/template/caps, but the inspected function does not itself check active `whatsapp_partner_optins` joined to the active partner. The automatic dispatcher must not reuse it until that is fixed and tested.
- **Stale dashboard language:** “External messages are not sent automatically”, “partner alerts remain subject to Owner review”, and “Owner Approval ALWAYS ON” conflate routine partner alerts with commercial commitments. Update only after implementation and tests make the actual distinction true; do not make a copy-only edit that suggests automation is ready while Meta remains NOT_VERIFIED.
- **Historical contradictions:** master plan/source-of-truth include older notes about an unconditional 409/410 pause, while the current local `src/whatsapp-sender.js` has live template-send logic and no such unconditional pause. Current code is the evidence for local implementation; dated notes must be marked historical rather than used as current source instructions. The latest deployed version recorded in the latest handover is `e534903c-9583-484a-9570-f2600dd3b3aa`; do not infer that every local source change is deployed.
- **No authenticated live tab verification:** current source audit cannot prove Seller, Buyer Discovery, Gmail inbox, partner consent rows, or current Meta diagnostics from the signed-in dashboard. Use read-only authenticated Owner evidence for those checks; never simulate it from public HTML or a 401 response.

1. Reconcile the canonical status/handover so current sender source and deployed version are not confused with older 409/410 notes.
2. Keep current fail-closed Meta verification. Obtain a fresh read-only Meta diagnostic from the already signed-in Owner dashboard; do not call registration/code endpoints.
